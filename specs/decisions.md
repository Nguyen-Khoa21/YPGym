# Open decisions

Each decision blocks or shapes a specific package. **On 2026-11-09 the owner approved every recommendation below** ("go with your recommendations"). The Decision column records that, and the package specs were updated to match.

| ID | Question | Blocks | Recommended | Decision |
|---|---|---|---|---|
| D-01 | How does the web client learn the gym of a manager or staff member? Today the user payload has no gym, and staff only see their gym through an open shift. | Package 6 (T6-03, T6-06) | Add an additive `GET /gyms/me` that returns the caller's effective gym. It leaves the user payload that the mobile apps use untouched. | Approved as recommended |
| D-02 | Browser-level tests: set up Playwright, or stay with `node --test` plus a manual script? `@playwright/test` is a devDependency, but there is no config, no e2e folder and no browser install step. | Package 5 (T5-12), Package 7 (T7-06) | Add a minimal Playwright config used only for the broadcast form and the dashboard responsive check, and document `npx playwright install chromium`. The Package 7 typing and layout criteria cannot be proven without a real browser. | Approved as recommended |
| D-03 | The admin class list, `GET /analytics/peak-hours` and `GET /attendance/crowdedness` quietly fall back to District 1 when an admin sends no gym. The attendance admin list instead treats "no gym" as all gyms. Keep the fallback or require an explicit gym? | Package 6 (owner views) | Require an explicit gym (422 `GYM_SCOPE_REQUIRED`) where the owner is comparing branches. A silent District 1 default can mislead an owner who thinks they are looking at everything. The web pages already send a gym. | Approved as recommended |
| D-04 | What does the member dashboard show for a user with no membership? Today it shows District 1 occupancy (`dashboard_service.py`). | Package 5 (T5-08) | Show no occupancy and no history. Show a prompt to buy a membership and choose a gym, which matches the rule that a gym is chosen at purchase. | Approved as recommended |
| D-05 | Package 4 has two untested behaviors: the payOS webhook moving a payment to `paid_review` when the gym went inactive, and `409 IDEMPOTENCY_KEY_REUSED` for a changed plan or gym. Add tests now? | Confidence in Package 4 | Add both as one small test-only commit before Package 5. They guard payment safety, and the code already exists. | Approved as recommended |
| D-06 | Should staff crowdedness be shift-gated too? The shift gate is specified for the attendance list and manual close only. Occupancy is already visible to members of that gym. | Package 6 (T6-02) | Leave occupancy ungated. The workspace still does not request it while locked. | Approved as recommended |
| D-07 | May a manager see revenue for their own branch? The master prompt blocks chain-wide revenue and billing for managers and says nothing about branch revenue. | Package 6 (T6-04) | Managers get branch membership, class and attendance figures but no revenue. Owner-only revenue is the safer reading and is easy to relax later. Either way, the current chain-wide summary must be fixed (finding G-08). | Approved as recommended |
| D-08 | When the owner opens the attendance page, default to one branch, or to all branches? The API supports both. | Package 6 (T6-08) | Default to one branch, with an "All branches" option and a visible gym column. | Approved as recommended |
| D-09 | Name and status of the shift error. | Package 6 (T6-02) | `403` with code `SHIFT_REQUIRED`, in the existing structured error format. | Approved as recommended |
| D-10 | Should `docs/HANDOFF_MULTIGYM_SESSION.md` be committed, rewritten, or deleted? It is untracked and describes Package 4 as unfinished. | Housekeeping | Replace it with a short current handoff after Package 5 starts, or leave it untracked. Do not commit the stale version. | Approved as recommended |

## Findings that need no decision

- **G-08 (security).** `GET /admin/analytics/summary` returns membership, class, attendance and revenue totals for all gyms, and it allows managers. This conflicts with the manager rule in the master prompt. It is fixed in Package 6 task T6-04 whatever D-07 says. Until then a manager can read chain-wide totals.
- The other gaps G-01 to G-07 are listed in [completed-packages.md](completed-packages.md) with the package that handles each.
